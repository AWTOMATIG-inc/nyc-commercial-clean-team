01The journey being built

  1. Customer signs upRegister, sign in, recover access. Company profile with two or more service properties.
  2. Requests serviceService catalog, conditional questions, frequency, requested date/time, secure attachments, review before submit. Gets a unique request ID. time = request until staff confirm
  3. Admin quotesCreate and revise quotes. Customer reviews and approves the current revision; earlier revisions stay linked.
  4. Customer paysOne-time Stripe payment (card / wallet where supported). Signed webhook records success or failure exactly once. idempotent
  5. QuickBooks syncsCustomer, invoice, and payment reference/status via OAuth. Failed sync is visible; an authorized admin can retry.
  6. Admin schedules & completesProtected dashboard: search, open, update status, confirm schedule, see payment and sync status, full activity history.
  7. Emails at every stepCustomer: receipt, quote, approval, payment result, confirmation, reminders, completion, invoice. Admin: new request, approval, payment, cancellation.

At each checkpoint the delivery lead records build state, evidence, open defects, dependencies, and next actions. The client validates journeys and reports reproducible failures; the team fixes and retests before a journey is marked complete.

03Rules that don't bend

Security

  • Role and ownership checks run server-side on every record and file.
  • Changing an ID in a URL or API call must never expose another customer's data.
  • HTTPS in production; rate limits and input validation.
  • Audit trail: actor, event, timestamp, state changes, with no secrets.

Payments & secrets

  • Never store full card numbers or CVC, in records or logs.
  • Provider-hosted/tokenized payment flows only.
  • Keys and OAuth tokens live only in protected env config. Never in git, client bundles, docs, or emails.

Architecture

  • Pages handle presentation; business rules live in server services/APIs.
  • Store stable cross-system IDs on the related records.
  • Files: type/size validated, linked to the request, time-limited links where supported.

Source of truth

  • MongoDB holds operational records.
  • Stripe decides transaction outcomes.
  • QuickBooks Online holds accounting records.

05What the client must provide

Access

  • Repository, VPS, database, test environment, all through an agreed secure method.
  • Stripe and QuickBooks Online test access, plus OAuth/account approvals.
  • Domain/DNS verification for production email.

Decisions (at the foundation checkpoint)

  • Service catalog and conditional intake questions.
  • Quote workflow and statuses.
  • Customer email content.
  • QuickBooks field mapping and sync direction.
  • Named UAT reviewers.

08When it's done

The delivery lead closes the work order once:
  1. The acceptance matrix and handover records are complete.
  2. Production deployment and smoke check are documented.
  3. Repository and account handover is confirmed.
  4. The 60-day defect-support window has been communicated to the client contact.

Post-launch support covers reproducible defects in accepted Phase 1 scope. New features, changed workflows, extra integrations, provider outages, and third-party config changes are not defects.
